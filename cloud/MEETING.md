# AI会议室：角色、记忆与研究提案

会议室默认随每日模拟盘运行，兼容现有 R2 状态，无需重新初始化账户。旧单角色复盘保存在历史 R2 版本中；补跑某天时，当前日报会更新为该日的会议汇总。

## 每天怎样运行

1. 程序完成行情检查、模拟结算和下一交易日计划冻结，并先保存到 R2。
2. 利弗莫尔、巴菲特、科斯托拉尼、AI进化四席独立读取同一份事实、共享记忆、各自记忆及既有提案。这一轮看不到其他席位当天的发言。
3. 最强AI阅读四席发言，交叉审计数据口径、结论冲突、证据缺口与重复想法。
4. 主持人汇总共识和分歧，合并共享记忆，提出最多三个待验证研究提案。没有新发现时允许零提案。
5. 结构校验通过后，保存会议、记忆和提案；报告包含会议摘要。

通常是每个交易日 **6次成功模型调用**，接口临时失败时可能额外重试。默认使用同一个 `AI_MODEL`、`AI_BASE_URL` 和 `AI_API_KEY`。角色是分析分工，不是五套独立运行的策略账户，也不代表五个独立模型的证据。

## 数据和方法的范围

当前会议读取账户结算、候选/计划、行情覆盖与研究记忆，尚未接入龙虎榜、财务三表、公告、新闻和外围市场事实；角色名称不表示拥有这些数据。`meeting_seed.json` 已纳入原 `premarket-3pick-plan` skill 的来源哈希与人工筛选的方法教训，重点是可知时间、事前/事后分离、缺失语义和龙虎榜口径。旧收益数字与交易参数没有迁移。完整核对见 [数据接口覆盖](DATA_SOURCES.md)。

更新 seed 仅影响之后首次创建的会议；已开始或完成的会议继续使用冻结输入，不会重写历史发言。

## 记忆如何延续

- `cloud/meeting_seed.json`：从原版资料整理的方法教训，附原文件相对路径和SHA256。只迁移方法教训，不搬入个人资料、完整聊天记录或未经重验的历史收益。
- `meeting/memory/YYYY-MM-DD.json`：当天共享记忆和五席各自的记忆，保留来源日期和事实摘要哈希。下一天读取最近一个更早日期的快照。
- 四席各自合并本席旧记忆；主持人合并旧共享记忆。旧观点被修正时应说明撤回，记忆始终标为研究观点。
- 历史补跑不会读取未来日期的记忆或提案，首次开始的会议会冻结其输入上下文。已完成会议的全部逐日快照保留，可追溯总结变化。
- 每次只向模型传递最多30个最近更新的提案、最多12条共享记忆、每席最多6条记忆，避免把无限增长的全文塞回模型。完整记录仍保存在R2。

## 提案不是交易指令

`research/proposals.json` 为可重建台账，`research/proposals.md` 可直接阅读。每个提案包含：

- 稳定ID、标题、可证伪假设、创建日期；
- 当前证据、验证计划、否定条件、所需数据；
- 历次讨论日期与来源会议；
- 程序固定状态 `pending_validation`，总开关 `auto_apply: false`。

相同标题和假设自动合并；延续旧问题时模型可引用已有ID，把补充意见追加到同一提案。语义相似但改写了标题和假设的内容仍可能形成重复提案，需在研究阶段核对。

本版本不会自动运行回测、批准提案、修改参数、解除暂停买入、改写账户或冻结计划。模型请求不提供工具或代码执行接口。交易引擎也不读取会议和提案。未来若要做策略进化，还需独立的回测、样本外验证与版本启用流程。

## 输出位置

以下路径相对运行状态目录；均随R2状态包保存：

```text
meeting/days/YYYY-MM-DD.json    冻结上下文、逐席结果、模型/用量、断点状态
meeting/days/YYYY-MM-DD.md      可读的发言、审计、共识、分歧和提案
meeting/memory/YYYY-MM-DD.json  共享记忆与各席记忆
research/proposals.json         累计待验证提案及历次讨论
research/proposals.md           可读提案台账
reviews/YYYY-MM-DD.json         主持人汇总及各环节调用信息
reports/YYYY-MM-DD.html         模拟账户日报与会议摘要
```

GitHub运行时，这些文件包含在 `daily-report-...` 附件中。服务器运行时，在 `/var/lib/wuming/runs/<运行编号>/state/` 查看。R2桶保持私有；模型会收到选股、账户事实和研究记忆，API密钥不会进入提示词。

## 调整角色与成本

编辑 `cloud/meeting.json`：

- `roles`：至少两个分析席位，最后一个必须是审计席位；最多六席。
- 各席 `focus`：分析职责。各席 `model` 留空沿用 `AI_MODEL`，也可填同一服务商兼容接口下可用的另一模型ID。
- `moderator_model`：主持人模型，留空同样沿用 `AI_MODEL`。
- `max_tokens` / `summary_max_tokens`：各席/主持人的单次输出上限。接口必须支持 Chat Completions 的 `max_tokens` 参数和文本JSON响应；不依赖厂商专用JSON模式。
- `proposal_context_limit`：送入模型的历史提案数。
- `enabled: false`：改用旧的单角色文字复盘；`--skip-ai` 则完全不调用模型。

费用取决于服务商与实际输入输出，用量保存在每席记录中。首次建议检查完整输出；如果模型经常输出截断内容，增加输出额度或缩短提示词。失败和格式错误会显式报错，不会把空回复当成成功。

已开始的同日会议继续使用保存的角色设置；修改配置通常从下一天生效。模型默认ID来自运行环境，实际使用的ID记录在每次响应元数据里。

## 中断与补跑

每完成一个环节就保存本地并提交R2，重跑复用已成功环节。AI出错不撤回已保存的模拟结算。主流程仍标记失败，便于定时重试和排查。

只补已有结算日的会议：

```bash
PYTHONPATH=cloud .venv/bin/python -m ashare_cloud.cli review \
  --date 2026-10-26 --state-dir .cloud-state-review-20261026
```

日期替换为实际已结算日，远端恢复目录须为空。此命令不采集行情、不模拟新成交、不改次日计划。服务器可改用 `ashare_cloud.runner --command review --date ...` 自动创建独立目录。

接口返回后、检查点上传前如果机器突然中断，该环节仍可能再次调用模型；不同机器同时启动也可能产生重复调用。因此只选一个日常调度端，R2的条件写入负责拒绝旧状态覆盖新状态，不保证API调用严格只发生一次。

若某天会议一直失败，下一天的交易流程仍可继续；会议只读取已完成的旧记忆。随后补完旧会议不会改写已经冻结的后续会议输入。
